# ADR-008 — Make review independent through fresh execution, minimal context, a credential-free model step, and an adversarial rubric

**Status:** Accepted — baseline

## Context

An implementer reviewing its own work is vulnerable to confirmation bias. A separate job that has a write-capable token available to the model could silently repair code rather than report a defect. A reviewer that sees an implementer's persuasive rationale may accept claims instead of testing them.

## Decision

Use the three-step review design in `autose-review.yml`:

1. **Prepare** uses the job's read-only GitHub token to fetch PR facts and diff, verifies that both PR head and base belong to the allowed repository, and checks out the exact head SHA.
2. **Review** starts on a fresh runner. Its model process has a model-provider credential only—no GitHub token. It sees the sanitized issue, diff, repository at PR head, and configured test command. It can write probes only below scratch.
3. **Post** deterministically publishes `review.md` as a PR review and applies outcome labels.

The reviewer prompt starts from a sceptical stance and requires: derive its own checklist from the issue, inspect diff and adjacent code, run the full suite, write at least one probe, and report concrete evidence. Approval is rejected by the harness unless the reviewer ran passing tests and all checklist items are met. A change request must include at least one blocker/major finding and route work to requirements, design, or implementation.

## Consequences

Review cannot inherit the builder's chain of thought, alter the branch, or approve without test evidence. It may still fail to find a bug, so five seeded PRs with labelled defects measure reviewer recall, precision, and false approvals. The `reviewer-sees-rationale` experiment is particularly valuable: if it increases approvals but reduces seeded-defect recall, preserve the baseline exclusion policy.
