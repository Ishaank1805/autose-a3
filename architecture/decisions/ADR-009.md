# ADR-009 — Treat issues, comments, PR text, and tool output as hostile data; stop safely on uncertainty or exhausted budget

**Status:** Accepted — baseline

## Context

Anyone can write issue text, and an issue can contain hidden instructions, malicious links, shell commands, requests for secrets, or scope expansion. Models may also loop, time out, or be unable to produce a testable specification. The assignment explicitly calls for prompt-injection and failure handling.

## Decision

The gate sanitizes issue titles, bodies, and trigger notes before creating the snapshot. Prompts wrap all human-authored content in `<untrusted_...>` tags and explicitly state that it is data rather than authority. Agents are told that code comments and command output are also untrusted.

The harness enforces the policy rather than relying on those instructions: it deny-lists risky commands, uses a credential-scrubbed environment, caps output at 12,000 characters, bounds commands to 300 seconds, and applies job/model budgets. Agents cannot ask arbitrary follow-up questions; if the Planner cannot state testable criteria, it calls `cannot_specify`, writes the reason/questions into `spec.md`, and the run stops for a maintainer. Similar `cannot_design`, invalid-test, failed-check, CI-timeout, model-error, and budget-exhaustion paths write an artifact and stop or take only a legal bounded retry.

## Consequences

The design fails closed: ambiguity or a suspicious instruction cannot become a broad repository-writing action. This can reduce automation on vague issues, which is the correct trade-off for a bot with write capability. Sanitization and deny-lists are not complete defences against all prompt injection or malicious code, so adversarial issue fixtures and the red-team issue should be run and reported as evidence, not treated as a proof of safety.
