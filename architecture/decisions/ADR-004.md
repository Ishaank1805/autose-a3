# ADR-004 — Store cross-job state as GitHub Actions artifacts and a live issue status comment, not in cache or uncommitted workspace state

**Status:** Accepted — baseline

## Context

GitHub Actions jobs run on fresh runners. The workflow needs to preserve outputs across the build, review, rework, and report jobs, and users need to follow a run without access to the runner filesystem. Caches are mutable, can be evicted, and are unsuitable as evidence. Committing temporary agent state into the PR branch would contaminate the change under review.

## Decision

Persist stage state in per-job artifacts:

- `autose-issue` holds the sanitized issue snapshot produced by the gate job.
- `autose-state-r<N>` holds build/rework state and stage artifacts for round `N`.
- `autose-review-r<N>` holds `review.md` and structured review data.
- `autose-run-summary` holds the final report and generated `sequence.mmd`.

Artifacts are retained for 90 days. `State` writes a history-tagged version when an artifact is regenerated. A live status comment on the issue mirrors current stage progress and links the Action run; the final report applies an outcome label.

The current baseline **does not promise automatic resume of an interrupted Actions run**. A GitHub job re-run or a new trigger creates a new execution context; artifacts are evidence and inputs for the explicitly wired rework jobs, not a general checkpoint-recovery system.

## Consequences

The state visible to the pipeline and the state visible to a maintainer are the same auditable artifacts. This satisfies the assignment's “follow a run” requirement and avoids cache correctness problems. The limitation is operational: after an unexpected failure a maintainer may need to retrigger rather than resume at an arbitrary state. The report should state this explicitly rather than claim resumability from the external setup script alone.
