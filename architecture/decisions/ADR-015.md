# ADR-015 — Enforce least privilege at process and sandbox boundaries within a shared build job

**Status:** Accepted (Supersedes ADR-005)
**Date:** 2026-11-24

## Context

ADR-005 originally asserted that write privileges were partitioned at the GitHub Actions job level, with the gate and review jobs restricted to read-only access and only the build job granted repository write permissions. However, a codebase audit of `.github/workflows/autose-build.yml` and `autose/secretstore.py` revealed that stages 1 through 5 (requirements, design, implementation, testing, and release) all execute inside the same GitHub Actions runner job (`build`).

Consequently, GitHub repository write tokens (`contents: write`, `pull-requests: write`) must be available during the build job for stage 5 (release) to push bot branches and open pull requests. If write separation were not enforced at the process boundary, untrusted code generated by the Implementer or Test Author could potentially access the runner environment and abuse repository credentials.

## Decision

Enforce least privilege through process-level credential isolation and filesystem sandboxing rather than across distinct GitHub Actions jobs:

1. **Job-Level Scope**:
   - `gate`: `contents: read`, `issues: write`, `pull-requests: write`.
   - `build` / `rework`: `contents: write`, `pull-requests: write`, `issues: write`, `actions: write`.
   - `review`: `contents: read`, `pull-requests: write`, `actions: read`.
   - `report`: `contents: read`, `issues: write`, `pull-requests: write`.
2. **Process Credential Scrubbing (`autose/secretstore.py`)**:
   - The runner workflow writes credentials to disk in private temporary files (`umask 077`).
   - `Secrets.load()` reads tokens into Python memory, immediately deletes the directory, and scrubs `os.environ` of sensitive keys (`GITHUB_TOKEN`, `GH_TOKEN`, `AUTOSE_GITHUB_TOKEN`, and `*_API_KEY`).
   - No GitHub token is exported to subprocess environments.
3. **Sandbox and Tool Boundaries (`autose/sandbox.py`, `autose/tools.py`)**:
   - Agents execute tool commands in a sanitized environment that denies network access, Git push operations, `gh` CLI commands, and `/proc` secret inspection.
   - Writable paths are constrained by stage: the implementer may modify only `tinydb/**` and documentation; the test author only `tests/test_issue_<N>.py`; the reviewer only `scratch/`.
   - `enforce()` automatically reverts out-of-policy modifications after stage completion.
4. **Deterministic Release Authority**:
   - The GitHub token is loaded from memory solely in stage 5 (`stages/release.py`) after all agent execution terminates.

## Consequences

Model processes cannot push commits, modify workflows, access repository credentials, or interact with GitHub APIs. The primary residual risk is that all stages share a single runner environment; a flaw in process-level scrubbing or subprocess isolation could expose in-memory credentials. This design eliminates the latency of runner re-allocation between stages 1–4 and stage 5 while maintaining robust privilege containment.
