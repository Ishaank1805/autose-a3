# ADR-005 — Enforce least privilege at job, process, tool, command, and path boundaries

**Status:** Superseded by ADR-015

## Context

The workflow can edit a repository, push a bot branch, open a pull request, and post reviews. Issue text is untrusted. Job-level GitHub permissions alone are insufficient because the build job needs write authority for deterministic release, while model calls must never be able to use that token.

## Decision

Use defence in depth as implemented by the bundle.

1. Workflow-level `permissions: {}` means each job declares its own permissions.
2. The gate job has read access plus issue/PR comment authority; the build job has the write permissions needed to push `autose/*`, create/update a PR, and dispatch CI; the review job has `contents: read`, `actions: read`, and PR-review authority.
3. The build harness stages credentials as files, loads them for deterministic release, and deletes them before model agents start. Planner, implementer, test-author, and reviewer model processes receive no GitHub token.
4. Tool wrappers enforce writable paths: the implementer may change only `tinydb/**`, `docs/**`, and `README.rst`; the test author only `tests/test_issue_<N>.py`; the reviewer only a scratch directory outside the checkout.
5. `enforce()` reverts out-of-policy modifications after a stage, even if an agent bypassed a normal edit tool.
6. The sandbox uses a scrubbed environment and denies Git write operations, `gh`, network utilities, privilege escalation, package installation, secret-oriented `/proc` reads, and protected harness paths.

## Consequences

No model process can push, comment, alter workflow files, inspect secrets, or merge. A compromised model can at most make a constrained local change which is rechecked before deterministic release. The build job is still a sensitive trust boundary because it holds credentials after agents have completed; bugs in the harness or workflow could matter. That residual risk belongs in the report's threats to validity.
