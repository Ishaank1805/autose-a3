# ADR-007 — Gate stages with deterministic checks; use LLM judgement only as bounded supporting evidence

**Status:** Superseded by ADR-011

## Context

An agent self-reporting “done” is not a valid SDLC gate. Yet not every property, especially the testability of natural-language criteria, can be decided solely by syntax. The assignment requires all acceptance criteria to be testable, the code to build, tests to pass, CI to pass before release, and review decisions to be evidenced.

## Decision

The harness owns stage decisions and applies these checks:

| Stage | Authoritative check |
|---|---|
| Requirements | Structural Given/When/Then + verification-line check; Haiku judge adds per-criterion testability feedback. The judge is advisory unless configuration makes it required. |
| Design | Every planned path exists or is marked new; every existing named function/class is found by AST; every acceptance criterion has a planned `test_ac<N>_*` test. |
| Implementation | Configured byte-compile/import build passes; pytest collection succeeds; out-of-policy changes are reverted. |
| Testing | A test exists for every criterion; the full JUnit suite passes; base tests still collect; fail-to-pass is measured by testing the new tests against base source. |
| Release | The harness commits/pushes the configured bot branch, PR is open, and explicitly dispatched `ci.yml` succeeds within 20 minutes. |
| Review | The reviewer must run pytest itself before approval, mark every requirement it derived from the issue as met, and have no blocker/major finding. |

The baseline uses a **soft** fail-to-pass policy: if no new test fails against base source, the test author gets one strengthening retry and the report records a warning rather than automatically stopping.

## Consequences

Most gates yield objective logs and machine-readable evidence, while the judge is constrained to a narrow role. Soft fail-to-pass avoids rejecting valid behavioural tests that happen to pass on the base commit, but reduces assurance; this must be reported as a limitation and can be changed to `hard` after evidence from runs. CI dispatch is necessary because pushes made with `GITHUB_TOKEN` do not automatically start ordinary workflows.
