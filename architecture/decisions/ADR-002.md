# ADR-002 — Use a deterministic controller: a state machine for stages 1–5 plus an unrolled GitHub Actions review DAG

**Status:** Accepted — baseline

## Context

The required flow includes gates, test-repair loops, returns to design, and at most two review-requested reworks. Letting an LLM decide transitions would make retry limits and stopping behaviour non-auditable. Conversely, encoding every individual repair iteration directly in YAML would be difficult to test and maintain.

The supplied implementation already divides the problem in two: `autose/orchestrator.py` controls stages 1–5 and `.github/workflows/autose.yml` expresses review/rework rounds as a finite GitHub Actions DAG.

## Decision

Use the harness—not an agent—as the authority for transitions.

- `gate` validates the trigger, actor, target repository, and sanitized issue snapshot.
- The build/rework job runs `orchestrator.py`, a deterministic state machine over requirements, design, implementation, testing, and release.
- Requirements and design allow at most three submissions each.
- Implementation/testing allow at most three implementation attempts per design, one test dispute, and one redesign.
- `autose.yml` explicitly unrolls `review_1 → rework_1 → review_2 → rework_2 → review_3`; configuration bounds requested changes to zero, one, or two.
- A reviewer finding names exactly one target stage: requirements, design, or implementation. The next rework starts there.
- The final report job labels and summarizes the outcome. No path invokes a merge endpoint.

## Consequences

The workflow has a finite, inspectable execution graph and hard retry budgets. The state machine is unit-testable without a live model, while GitHub makes review-round dependencies visible in the Actions UI. The price is a more elaborate YAML DAG and a maximum of three reviews rather than unlimited reviewer negotiation. The `no-review-loop` variant supplies a D2 experiment: it compares the value of rework against its added cost and latency.
