# ADR-011 — Enforce deterministic stage gates with documentation-only plan exceptions and blocking LLM judge verdicts

**Status:** Accepted (Supersedes ADR-007)
**Date:** 2026-11-22

## Context

ADR-007 specified deterministic stage checks and asserted that the LLM testability judge is purely advisory unless explicitly configured as required. However, operational runs and codebase auditing revealed two significant structural issues:

1. In Campaign 1, red-team run [44741723040](https://github.com/Ishaank1805/tinydb/actions/runs/44741723040) stopped at the design stage with the error: "the plan still failed its check after 3 submissions". The design checker rigidly required every submitted plan to name at least one existing or new Python function in an editable source file. Consequently, issues whose resolution required modifying only documentation or configuration files could never satisfy the design gate.
2. In `autose/stages/requirements.py` (lines 25–41), the testability judge verdict is actually blocking when the judge model successfully executes: if the judge returns `testable: False` for any acceptance criterion, the harness appends the failure reason to `result.problems` and marks `result.passed = False`, rejecting the specification submission. The judge is advisory only in the failure mode where the LLM call raises an exception or fails to return structured JSON.

## Decision

Update and formalize the stage gating policy as implemented:

- **Documentation-Only Plan Exception (PR #23)**: Update `checks.check_design` so that if all files planned for modification match documentation patterns (`docs/**`, `*.rst`, `*.md`), the requirement to name Python functions and classes is bypassed. Plans modifying code files (`tinydb/**`) must still name valid AST functions. Fail-to-pass test runner resets both code and documentation files.
- **Blocking Testability Judge**: Formally acknowledge that `judge_testability` in `autose/checks.py` operates as an authoritative gate when online. Each acceptance criterion must pass both structural Given/When/Then checks and the judge's classification before the specification is accepted.
- **Retry Bounds**: Requirements and design remain bounded to at most 3 submissions each before the run stops cleanly.
- **Soft Fail-to-Pass**: Maintain the soft fail-to-pass policy at testing, granting one strengthening retry if no new test fails against the base commit.

## Consequences

The documentation-only exception allowed documentation issues, including the red-team security challenge, to pass design and complete the pipeline. In Campaign 2, run [44915278834](https://github.com/Ishaank1805/tinydb/actions/runs/44915278834) passed design and successfully opened PR #33. Across four post-fix red-team runs, two passed design while two were rejected for malformed structures, proving that the relaxed gate does not permit invalid plans. The blocking judge ensures criteria ambiguity is caught early at the cost of vulnerability to judge misclassification.
